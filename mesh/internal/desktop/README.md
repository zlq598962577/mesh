# mesh/internal/desktop — 桌面操作原语

所有桌面客户端适配器共用的底层原语：全局桌面操作锁、焦点管理、文本注入、三阶段发送协议。

本包只做"在 Windows 上安全地操作别人的窗口"这一件事。它不认识任何具体客户端（微信、飞书、Telegram、Discord），客户端的差异全部由适配器层通过本包定义的接口注入。

### 0.1 `go vet` 保留的告警及理由

`go vet ./internal/desktop/...` 目前剩 **1 条**告警：

```text
internal/desktop/win32.go:379:9: possible misuse of unsafe.Pointer
```

位置是 `lockGlobalMem` 里的 `return unsafe.Pointer(r), nil`，`r` 来自紧邻的 `procGlobalLock.Call`。

**保留而不改写的理由：**

1. `r` 是 `GlobalLock` 返回的系统内存句柄，指向 `GlobalAlloc` 分配的**非 Go 堆内存**。`unsafeptr` 检查担心的是"uintptr 存活期间 GC 移动了对象"，而系统内存不会被 GC 移动，该风险在此不成立。
2. `r` 直接来自紧邻的 `.Call` 返回值，中间没有指针运算、没有再分配内存，只有一次不改变值的 nil 判断，满足 `unsafe.Pointer` 文档给出的合法转换条件。
3. 唯一能消掉告警的写法是把 `&r` 用 `*(*unsafe.Pointer)(unsafe.Pointer(&r))` 重新解释——语义完全相同，纯粹为了糊住 linter，反而把"这是一个系统句柄"的意图藏起来。宁可留一条有解释的告警，也不要写一段为了骗过检查而更难懂的代码。

如果有人后续要清理这条告警，请先确认上面的第 1、2 条仍然成立，并同步更新本节。

## 1. 硬性技术约束

| 约束 | 原因 |
| --- | --- |
| 只用 Go 标准库 + `syscall` / `unsafe` 直调 Win32 | 必须 `CGO_ENABLED=0` 可编译 |
| 禁止 `golang.org/x/sys` | 项目依赖白名单里没有它 |
| 禁止 cgo | 同上，且交叉编译需要 |
| 所有等待必须响应 `context` | 用户取消后不许在后台傻等 |
| 共享类型只从 `mesh/internal/contract` 导入 | 该包是冻结的，只读 |
| 不关闭用户自己的窗口 | 只释放自己持有的句柄 |

本包内部唯一允许的非 `context` 等待是 `rawSleep`，它只在剪贴板恢复路径上使用（见 §5.3），并且有明确注释说明为什么在那里不能响应取消。

## 2. 全局桌面操作锁：段落式持有

### 2.1 为什么需要锁

前台窗口全系统只有一个，剪贴板全系统只有一个。两个 bot 同时打字，结果一定是两边的字混进同一个输入框，而且事后无法区分谁是谁的。所以聚焦、键盘、鼠标、剪贴板这四类动作必须串行。

### 2.2 最容易做错的地方：持有粒度

这是整个适配器层最容易写错的一点，请务必读完这一节。

**错误做法：会话式持有。**

```
Acquire ──► 聚焦 ──► 注入 ──► 提交 ──► 等客户端生成完（几十秒~几分钟）──► 读结果 ──► release
                                      ▲
                                      └── 锁被独占这么久，其他 bot 全部排队
                                          用户切走窗口 → 我们的焦点预检失败 → 用户被锁死
```

客户端生成一轮可能要几分钟。这期间锁被一个 bot 独占，其他 bot 全堵住，用户自己也没法用那个窗口。这等于把用户的电脑锁死了。

**正确做法：段落式持有。**

```
时间轴 ──────────────────────────────────────────────────────────►

段落 A          段落 B                      段落 C
[持锁]          [不持锁]                     [持锁]
聚焦+注入+提交   等客户端生成内容             聚焦+核实结果
几十~几百毫秒    几十秒~几分钟                几十~几百毫秒
   │                 │                           │
   └── release() ────┘                           │
                     其他 bot 可以自由使用桌面     │
                     用户可以切窗口/复制粘贴       │
                                                 └── release()
```

关键点：**段落 B 必须完全在锁外。** 等待期间其他 bot 可以自由使用桌面，用户可以自由切窗口、复制粘贴、干自己的活。

这也是本包**刻意不提供**"持有到发送完成"这种便利 API 的原因——那种 API 会诱使调用方写错。

### 2.3 代码形态

```go
// 段落 A：只做需要焦点的动作
release, err := desktop.AcquireDesktop(ctx)
if err != nil {
    return err
}
defer release()   // 兜底，异常路径也一定释放

if err := desktop.EnsureForeground(ctx, hwnd, desktop.FocusOptions{}); err != nil {
    return err
}
if err := sender.Prepare(ctx, target, text); err != nil {
    return err
}
if err := sender.Submit(ctx, target); err != nil {
    // 注意：这里不能直接重发，必须先 Verify
}
release()         // 段落 A 结束，立刻释放

// 段落 B：等待客户端生成 —— 不持锁，可能几分钟
// （这里什么都不做，或者做与桌面无关的事）

// 段落 C：重新取锁去核实
release2, err := desktop.AcquireDesktop(ctx)
if err != nil {
    return err
}
defer release2()

result, err := sender.Verify(ctx, target, text)
```

### 2.4 其它锁语义

- **包级单例。** `desktopLock` 类型不导出，外部包造不出第二把锁，也就无法绕过串行化。
- **release 幂等。** 内部 `sync.Once`，重复调用安全。所以 `defer release()` 和显式提前 `release()` 可以共存——这正是段落式持有需要的：段落 A 结束后要立刻释放，但异常路径上还得靠 defer 兜底。
- **不可重入。** 同一 goroutine 连续 `AcquireDesktop` 两次会阻塞到 ctx 超时。这是刻意的：重入会让"哪里真正持有锁"变得不可推理，而段落式持有的正确性完全依赖持有时长可测量。需要嵌套时请把逻辑合并到一个段落里。
- **等待可打断。** 内部用带缓冲 channel（容量 1）而不是 `sync.Mutex`，因为 `Mutex.Lock()` 无法被 context 打断。这是唯一能同时满足"互斥"和"context 超时"的标准库原语。
- **拿不到锁时什么都没做。** 返回 `ErrLockTimeout` 时我们一个字节都没往目标窗口写，调用方可以安全地稍后重试或降级。错误信息里会带上"谁占着锁、占了多久"，便于区分"别的 bot 在打字"和"我们自己某处忘了释放"。
- **失败不要无限重试。** `AcquireDesktop` 超时后应当放弃本次操作并如实上报，而不是循环重试——无限重试在锁竞争激烈时会形成活锁。

## 3. 发送协议：三阶段

### 3.1 状态图

```
                        ┌──────────────┐
                        │   初始状态    │
                        └──────┬───────┘
                               │
                               ▼
                     ┌───────────────────┐
              ┌─────►│  1. Prepare 准备   │  等客户端就绪 → 注入文本（不提交）
              │      └─────────┬─────────┘
              │                │
              │      ┌─────────┴─────────┐
              │      │ 失败              │ 成功
              │      ▼                   ▼
              │  ┌────────┐      ┌───────────────────┐
              │  │ Verify │      │  2. Submit 提交    │  按回车（可能已送达！）
              │  └───┬────┘      └─────────┬─────────┘
              │      │                     │
              │      │           ┌─────────┴─────────┐
              │      │           │ 失败/超时         │ 成功
              │      │           ▼                   ▼
              │      │      ┌────────┐       ┌───────────┐
              │      │      │ Verify │       │ 3. Verify │
              │      │      └───┬────┘       └─────┬─────┘
              │      │          │                  │
              │      └──────────┴──────────────────┤
              │                                    │
              │        ┌───────────────────────────┼───────────────────────┐
              │        │                           │                       │
              │        ▼                           ▼                       ▼
              │  ┌───────────┐              ┌────────────┐          ┌─────────────┐
              │  │ Verified  │              │NotVerified │          │   Unknown   │
              │  │  已确认   │              │  确认未达  │          │   无法判断  │
              │  └─────┬─────┘              └──────┬─────┘          └──────┬──────┘
              │        │                           │                       │
              │        ▼                           ▼                       ▼
              │   ┌─────────┐              还有重发次数？            ┌─────────────┐
              │   │  成功   │               是 │    否               │ 禁止重发    │
              │   └─────────┘                  ▼     ▼              │ 如实上报未知│
              │                         回到 Prepare  ┌────────┐    └─────────────┘
              └───────────────────────────────────────│  失败  │
                                                      └────────┘
```

### 3.2 三个阶段的职责

| 阶段 | 做什么 | 失败意味着什么 |
| --- | --- | --- |
| `Prepare` | 等客户端进入可提交状态，把文本写进输入区，**不提交** | 文本可能还没进去，也可能进去了一半 |
| `Submit` | 提交（按回车） | **可能已经送达**，绝不能当成没送达 |
| `Verify` | 核实客户端里真的出现了本条请求 | 核实失败 ≠ 没送达，只能算 Unknown |

把"写文本"和"发送"分开的核心原因：**写文本可以安全重试**（覆盖式写入不产生重复提交），**发送不能**。

### 3.3 绝对禁止盲目重发

桌面客户端没有幂等键。按下 Ctrl+V 之后如果等待超时，无法区分：

- **(a)** 按键没送达，客户端什么都没收到 → 重发是对的
- **(b)** 按键送达了，客户端正在生成 → 重发会让同一句话被提交两次

情况 (b) 的后果不是"多发一条消息"，而是客户端可能把第二次提交当成新的对话轮次，生成两份回答；或者输入框里残留上一条内容，两次文本被拼接成一段语义错乱的话发给模型。用户看到一个精神分裂的 bot，而且很难理解为什么。

所以规则是硬性的：**`Submit` 返回超时后必须先调 `Verify`。**

| Verify 结果 | 允许重发？ |
| --- | --- |
| `Verified` | 不重发（已送达） |
| `NotVerified` | 可以重发 |
| `Unknown` | **不重发**，如实上报 |

代码里把这个规则编码进了类型：`VerifyResult.IsRetryable()` 只有 `NotVerified` 返回 true。调用方想知道能不能重试时不该自己写 `if result != Verified`——那会把 `Unknown` 也当成可重试，正好踩中最想避免的坑。

### 3.4 明令禁止的启发式

> **禁止**"等待 N 秒，如果这段时间内目标区域没有出现新字符，就认为已经生成完毕"。

这个启发式在本项目中明确禁止，后续维护者不得以"提高效率"或"改善体验"为由把它加回来。理由是它不是"不够精确"，而是**在原理上无法成立**：

1. **思考停顿与生成结束在屏幕上不可区分。** 正在推理的模型可能安静十几秒，已结束的生成可能立刻就安静了。字符静默期这个信号本身不携带"是否结束"的信息，任何阈值都是在猜。
2. **慢模型 + 长回答必然被误判。** 回答越长、模型越慢，静默期越长，被误判成"已完成"的概率越高——恰好在我们最需要耐心的时候最容易出错。这个错误方向是系统性的，调大阈值解决不了。
3. **它把"未知"伪装成"成功"。** 一旦上层拿到 `Success=true` 就不会再核实，错误结果一路流到用户面前，且没有任何地方留下"这可能是假的"的痕迹。这直接违反本项目"诚实上报未知"的底线（参见 `contract.FinalInfo.Unverified` 与 `contract.Usage.Known`）。
4. **它让故障不可观测。** 超时和正常完成会产生完全相同的日志，真实故障率永远无法从数据中看出来。

正确做法只有一个：向客户端要一个**明确的可观测信号**（生成中指示器的出现与消失、停止按钮的可用状态、消息计数的变化等），由适配器层的 `Verifier` 实现读取。拿不到明确信号时返回 `Unknown`，让上层决定是否提示用户"这个结果没被确认"。

**未知是允许的答案；假装知道不是。**

## 4. `unknown` 的传播规则

`VerifyResult` 是三值枚举而不是 `bool`，理由与 `contract.OperationState` 里的 `OpUnknown` 完全一致：桌面自动化的很多失败是"我们不知道"。把它折叠成 `false` 会让上层误以为"确定没成功"从而安全地重试，而实际上可能已经成功了。

### 4.1 向上传播路径

```
Verifier.VerifyText
        │
        ├─ 明确证据 ──► Verified / NotVerified
        │
        └─ 读不到 / 状态在变 / 核实过程出错 / 返回未定义值
                        │
                        ▼
                    Unknown  ← 任何一条不确定路径都收敛到这里
                        │
                        ▼
                SendOutcome.Result = Unknown
                        │
                        ▼
                SendOutcome.NeedsUserAttention() == true
                        │
                        ▼
        contract.FinalInfo.Unverified = true（适配器层职责）
        contract.Usage.Known = false（若涉及用量统计）
                        │
                        ▼
                 UI 如实展示"本次结果未确认"
```

### 4.2 规则

1. **`Unknown` 绝不降级成 `Verified`。** 没有核实能力时（`verifier == nil`），`Verify` 返回 `Unknown` 加错误，绝不返回 `Verified` 来"让流程走完"。
2. **`Unknown` 绝不降级成 `NotVerified`。** 核实过程本身出错（窗口消失、控件读不到）不能推断成"没送达"——那会导致重发。
3. **`Unknown` 时禁止重发。** `Send` 收到 `Unknown` 立即返回，不再循环。
4. **`Unknown` 必须向上暴露。** 适配器层必须把它映射到 `contract.FinalInfo.Unverified = true`，不许在中间层吞掉。
5. **`Verifier` 返回 `Unknown` 时不要返回错误。** `Unknown` 是合法的、诚实的答案，不是异常。返回错误会诱使上层把它当成"核实失败，重试核实"，从而掩盖真相。

### 4.3 `Verifier` 实现方约定

- 只在有**明确证据**时返回 `Verified` / `NotVerified`。
- 任何不确定（控件读不到、状态在变、刚提交还没来得及渲染）都返回 `Unknown` + `nil`。
- 不要为了"给个答案"而猜。

## 5. 文本注入

### 5.1 两条路径

| 路径 | 何时用 | 风险 |
| --- | --- | --- |
| **控件直设**（UIA ValuePattern） | 首选。目标有可访问的输入控件 | 低：不碰剪贴板，不模拟按键 |
| **剪贴板 + Ctrl+V** | 降级。控件直设不可用或失败 | 中：污染用户剪贴板，需要恢复 |

`Inject` 会先尝试 `TextTarget.SetValue`，失败后降级到 `InjectViaClipboard`。`StrictInject` 只走控件直设，绝不碰剪贴板。

`TextTarget` 在本包里**只是一个接口声明**：

```go
type TextTarget interface {
    SetValue(ctx context.Context, text string) error
}
```

UIA 的 `ValuePattern` 实现属于适配器层——那需要 COM 接口调用、vtable 偏移、`BSTR` 管理，放在这个只依赖 `syscall` 的包里会把复杂度炸开。

**`SetValue` 返回 error 的含义是不确定的**：它可能已经写入了部分文本。调用方必须 `Verify`，不许直接重发。

### 5.2 剪贴板恢复

降级路径的完整流程：

```
1. 记录当前剪贴板文本内容 + 序号（写入前）
2. 先注册 defer 恢复原内容 ← 必须在改动剪贴板之前
3. EmptyClipboard + SetClipboardData(CF_UNICODETEXT, 我们的文本)
4. 写入成功后记录此刻序号（作为基准）
5. 重新确认目标窗口仍在前台（不在前台就中止，不按 Ctrl+V）
6. 按 Ctrl+V
7. 等 PasteSettleDelay 让粘贴有机会完成
```

第 2 步排在第 3 步之前不是风格问题，是正确性问题：`EmptyClipboard` 与
`SetClipboardData` 是两次独立调用，**前者成功、后者失败**时剪贴板已经被清空。
如果恢复逻辑在写入之后才注册，这条失败路径就没有兜底，用户复制的文本会永久
丢失。所以 defer 必须先注册。

### 5.3 已知限制（重要，不要当成 bug）

1. **非文本剪贴板内容不会被恢复。** 如果用户剪贴板里是图片、文件列表、富文本，我们只读取 `CF_UNICODETEXT`，恢复时也只能写回纯文本。用户原本的图片会丢。这是本包已知的、未解决的限制。缓解手段：优先走控件直设路径；对剪贴板敏感的场景用 `StrictInject`。
2. **恢复用 `rawSleep` 而不是 `sleepCtx`。** 这是本包唯一允许的非 context 等待。原因：如果 ctx 在粘贴之后被取消，我们仍然必须把用户的剪贴板还回去，否则用户的剪贴板被永久污染。恢复是最多 3 次、每次几十毫秒的短操作，不会导致长期挂死。
3. **用户在我们写入后立刻复制了别的东西时，不恢复。** 通过比较 `GetClipboardSequenceNumber()` 判断：写入完成后我们记一次序号作为基准，恢复前再取一次；如果变了，说明用户在此期间复制了新内容，此时恢复会覆盖用户的新内容——所以选择不恢复，尊重用户的最新操作。注意基准是"写入之后"的序号，而不是"写入之前 +1"：`EmptyClipboard` 与 `SetClipboardData` 各自都可能让序号前进，增量并不稳定。
4. **写入失败路径也会恢复。** 如果 `EmptyClipboard` 成功但 `SetClipboardData` 失败，剪贴板已被清空且我们返回错误——此时恢复逻辑仍然会执行（判定条件是"序号已偏离写入前的值"），把用户的原内容写回去。这条路径曾经是有缺陷的（defer 注册在写入之后，导致失败时用户内容永久丢失），现已修正。
5. **`KeepClipboard` 选项可以让调用方完全放弃恢复**（零值是"恢复"，即默认尊重用户）。适用于明确知道自己在污染剪贴板、且愿意承担的场景。
6. **`OpenClipboard` 被占用时按有界重试处理。** 剪贴板同一时刻只允许一个进程打开。我们用 `ClipboardOpenTimeout`（默认 1.5 秒）+ `ClipboardRetryInterval`（默认 40 毫秒）重试，耗尽后返回 `ErrClipboardBusy`。不会无限重试。
7. **`PasteSettleDelay` 不是成功信号。** 它只是让粘贴有机会完成，好让后续 `Verify` 能看到变化。判断成功与否永远是 `Verify` 的职责。

## 6. 焦点管理

### 6.1 保存与恢复

```go
fg := desktop.SaveForeground()          // 记录当前前台窗口，永不返回 nil
defer fg.Restore(ctx)                   // 操作后恢复，best-effort
```

`Restore` 在下列情况是 no-op：`fg` 为 nil、记录的句柄为 0、窗口已被用户关掉、目标已经是前台。**它永远不会关闭任何窗口。**

### 6.2 预检：绝不打字到错误窗口

`Preflight(hwnd)` 按固定顺序检查，任一失败就返回结构化错误：

```
hwnd == 0 ?          → FocusWindowGone
IsWindow 失败 ?      → FocusWindowGone
锁屏（或无法判定）?   → FocusScreenLocked
IsIconic ?           → FocusWindowMinimized
!IsWindowVisible ?   → FocusWindowNotVisible
```

错误类型是 `*FocusError`，带 `Kind`、`HWND`、`Detail`，用户可读原因由 `focusKindText` 提供。用 `IsFocusErrorKind(err, kind)` 判定，不要比较字符串。

**失败关闭策略（fail-closed）**：无法判定锁屏状态时按"已锁屏"处理。理由是把字打进锁屏界面（或打进用户解锁后看到的第一个窗口）比拒绝操作糟糕得多。

### 6.3 抢焦点

`EnsureForeground(ctx, hwnd, opts)` 要求调用方**已持有桌面锁**（内部断言 `Held()`），然后：

1. 可选：`ShowWindow(SW_RESTORE)` 还原最小化窗口，并重新预检
2. 尝试抢焦点：`AttachThreadInput` 把本线程附加到当前前台窗口的输入队列，再 `SetForegroundWindow`，最后总是 `defer` 分离
3. 轮询直到前台窗口确实是目标，或超时（默认 2 秒）

Windows 有前台锁限制：后台进程不能随意抢焦点。`AttachThreadInput` 是标准的绕过手段，但不是 100% 可靠——某些情况下仍会失败，此时返回 `FocusDenied`。

**不抢占用户手动切换的窗口。** 如果用户在我们要操作期间切走了窗口，预检/前台校验会失败，我们中止本次操作，而不是把焦点硬抢回来。

## 6.4 按键：`PressKey` 与 `keybd_event` 的全局注入风险

### 6.4.1 为什么按键必须和打字走同一套纪律

`keybd_event` 是**全局注入**：它不认窗口，把按键送进当前前台窗口。也就是说，"往目标客户端按一个 Esc" 和 "往用户正在打字的文档里按一个 Esc" 在系统层面是同一个动作，区别只在于调用那一刻前台是谁。

这带来一个和 §6.2 同类的风险，但更隐蔽：`Inject` 打错窗口，用户看得见自己输入框里多了字；而 Esc 打错窗口，用户可能只是发现自己正在编辑的内容被取消/关闭了，未必能立刻归因到我们。

因此 `PressKey` 不是裸导出 `keyPress`，它强制走与发送协议完全相同的焦点纪律，顺序不可省：

1. `AcquireDesktop`（若调用方未持有锁；用 `Held()` 判断，因为锁**非重入**）
2. `SaveForeground` 记下当前前台，`defer RestoreForeground` 还原
3. `EnsureForeground(ctx, hwnd, opts)` 聚焦并**校验前台确实是目标窗口**
4. **发送前再校验一次** `foregroundWindow() == hwnd`
5. `keyPress(vk, false)` / `keyPress(vk, true)` 按下并抬起

第 4 步是刻意的重复校验：第 3 步到第 5 步之间仍有时间窗口（聚焦刚成功，用户手快切走了）。这一步失败直接返回 `FocusNotForeground`，**绝不盲发**。

### 6.4.2 只导出 `PressKey` / `PressEscape`，不导出虚拟键码表

`vkEscape` 等虚拟键码常量**不导出**。导出键码表等于鼓励上层自己拼 `Ctrl+W`、`Alt+F4` 这类组合键——那些组合键会关闭窗口或退出程序，后果远超"按一个功能键"。当前只提供 `PressEscape`，语义唯一且可审计。

如果后续确实需要别的单键，应当**逐个**加具名函数（例如 `PressTab`），而不是把键码表交出去。

### 6.4.3 `PressKeyOptions.RestoreMinimized` 默认 `false`

`EnsureForeground` 有能力把最小化窗口还原，但 `PressKey` 默认**不**这么做。原因：把一个最小化窗口弹到用户眼前是有明显存在感的界面干扰，是否可接受属于调用方的产品决策，不该由底层原语替它决定。适配器需要时可以显式打开。

### 6.4.4 错误返回不代表"没按下去"

`PressKey` 返回 error 时，**不保证按键没有被发送**。可能的情况包括：按键已注入、但随后的焦点校验或恢复失败。调用方不能把 error 当成"操作未发生"，只能当成"操作结果不可知"。这一条直接影响适配器层的 `Cancel` 语义，见 §6.4.5。

### 6.4.5 对适配器 `Cancel` 的后果：两态，都不许标成功

本机实测 UIA 控件枚举全空（见 `adapters/README.md` 的能力表），读不到客户端"是否还在生成"的状态。因此 `Cancel` 只能有两种诚实的结局：

| `PressEscape` 结果 | 适配器应报 | 语义 |
| --- | --- | --- |
| 成功 | "停止待确认"，`StopUnconfirmed = true` | **已请求未证实**：Esc 已发出，但客户端界面不可读，无法核实生成是否真的停了 |
| 失败（聚焦失败/锁不可得） | "未发送停止请求，请在客户端窗口手动停止" | **未发送**：什么都没做，必须由用户手动处理 |

两种都**不得**标记为成功。差别在于诚实度：第一态至少让用户知道平台已经尽力，第二态明确告诉用户平台没做到、需要人介入。把它写成"已停止"是欺骗——我们没有任何证据。

另一个必须守住的边界：**取消绝不靠杀进程**。杀客户端会丢掉用户其它会话、未保存内容，并且违反 `contract.Engine` 的 `Cancel` 约定（§9.2 明令禁止用 Job Object 整组杀）。按 Esc 是唯一允许的手段，做不到就如实报告做不到。

## 7. 必须在真实硬件上验证的清单

**状态更新：** 本机现已具备 Go 工具链（`go1.27.4 windows/amd64`），编译、`go vet`、锁测试均已真实执行并通过（见 §0）。以下清单中**依赖活的桌面会话与真实客户端窗口**的部分仍未经自动化验证，第一次在目标机器上使用时请按顺序核对：

### 7.1 编译

- [ ] `go build ./...` 通过。重点看 `syscall.NewLazyDLL` / `NewProc` 的调用参数个数与类型。
- [ ] `go vet ./...` 通过，重点看 `unsafe.Pointer` 转换。
- [ ] `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build ./...` 通过。

### 7.2 锁（唯一能跨平台验证的部分）

- [ ] `go test ./internal/desktop/ -run Test` 通过。这组测试不依赖 Win32，任何平台都能跑。
- [ ] 若 `TestMutualExclusion` 在 CI 上偶发失败，检查是否是 2 秒期限太紧，而不是互斥真的坏了。

### 7.3 Win32 常量与结构

- [ ] `cfUnicodeText = 13`、`gmemMoveable = 0x0002`、`swRestore = 9`、`keyeventfKeyUp = 0x0002`、`uoiName = 2` 等常量值正确。
- [ ] `GetClipboardData` / `SetClipboardData` 返回的 `HANDLE` 被正确当作 `uintptr` 传递，没有误当成指针。
- [ ] `GlobalAlloc` 之后 `SetClipboardData` 成功时**不**再 `GlobalFree`（所有权已转移）；失败时必须 `GlobalFree`，否则泄漏。这条极易写错，请重点看。
- [ ] `GetWindowTextW` 的缓冲区长度按 UTF-16 码元计算，不是字节。

### 7.4 剪贴板

- [ ] 复制一段中文，跑一次 `InjectViaClipboard`，确认原内容被恢复。
- [ ] 剪贴板里放一张图片，跑一次注入，确认**已知限制**：图片丢失（这是当前设计取舍，不是 bug，但需要产品确认可接受）。
- [ ] 用另一个进程占住剪贴板，确认 1.5 秒后返回 `ErrClipboardBusy`，而不是永久挂起。
- [ ] 注入后立刻手动 Ctrl+C 复制别的东西，确认原内容**不会**被恢复覆盖（序列号检查生效）。

### 7.5 焦点与锁屏

- [ ] 目标窗口最小化时，确认返回 `FocusWindowMinimized`，而不是把字打进去。
- [ ] 目标窗口在后台时，确认 `EnsureForeground` 能抢到焦点；抢不到时返回 `FocusDenied`。
- [ ] 锁屏状态下确认返回 `FocusScreenLocked`，**且没有任何按键被发出**。
- [ ] 双显示器、多虚拟桌面场景下确认前台判断正确。
- [ ] RDP 会话断开/重连后确认锁屏检测仍然正确（已知可能误判，见 §6.2 限制）。

### 7.6 发送协议

- [ ] 客户端生成中按回车，确认 `Ready` 返回 false 且 `Prepare` 会等待。
- [ ] 人为让 `Verifier` 返回 `Unknown`，确认**不会**重发（这是最关键的一条）。
- [ ] 人为让 `Verifier` 返回 `NotVerified`，确认会重发，且重发次数不超过 `MaxResends`。
- [ ] `Submit` 之后立刻杀掉客户端进程，确认落到 `Unknown` 而不是 `NotVerified`。

## 9. 未实现的部分及原因

以下功能**没有实现**，不是遗漏：

| 未实现 | 原因 |
| --- | --- |
| UIA `ValuePattern` 的具体实现 | 需要 COM 接口、vtable 偏移、`BSTR` 管理，属于适配器层。本包只声明 `TextTarget` 接口。 |
| 鼠标操作原语 | 当前所有适配器都用键盘路径。加鼠标需要处理坐标缩放、DPI 感知、多显示器负坐标，在没有工具链的情况下风险高于收益。锁已经预留了串行化位置。 |
| 非文本剪贴板内容的保存/恢复 | 需要枚举所有剪贴板格式并逐份复制，代码量大且难以在无工具链环境下保证正确。当前明确记为已知限制（§5.3）。 |
| 冲突检测与草稿保留（方案 §4.2.2 第 5 条） | 需要"如何判断窗口被用户占用"的客户端特定知识（光标位置？输入框非空？），无法在通用层实现。本包提供了它需要的基础设施：`Preflight` 检测状态不符、`FocusError` 携带明确原因、注入路径不覆盖非空输入区之外的任何内容。真正的"暂停并保留草稿"逻辑由适配器层用这些原语组装。 |
| 窗口内容 OCR / 截屏核实 | 需要 GDI 或 Desktop Duplication，且 OCR 结果本身不可靠，会把 `Unknown` 伪装成 `Verified`（违反 §3.4 的精神）。核实必须基于客户端明确的可观测信号。 |
